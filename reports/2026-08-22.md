## 数据口径与限制

1. **24 小时新增 Star**：采用 GitHub Trending 日榜观察时刻显示的 `stars today`，属于滚动窗口近似值。
2. **7 天新增 Star**：采用周榜显示的 `stars this week`。未进入周榜可见范围时标记“缺失”，不使用累计 Star 倒推。
3. **窗口异常**：`modular` 的周榜值 744 小于日榜值 905，说明日榜、周榜抓取/刷新时点不一致；原值保留并标为异常，不能相加。
4. **Fork**：累计 Fork 来自本期仓库 API 快照；对 8 个连续上榜项目，以本期减上一期快照得到约 24h Fork 增量。该差值受两次采样时点影响，均标为“快照估算”；新上榜项目的 Fork 增量缺失。
5. **贡献活跃度**：近 7 天提交数来自最近 100 条提交的时间过滤；若达到 100，记为“≥100（截断）”。近 7 天新建 Issue/PR 来自 GitHub Search 的 `created:>=2026-08-15` 计数，包含已关闭项目与机器人活动，不能等同于独立贡献者人数。
6. **讨论热度**：统一列出近 7 天新建 Issue/PR 和 Discussions 是否启用；未取得同口径的 Discussion 新增/评论数。累计开放项为 Issue 与 PR 合计快照。
7. **相对日增**：按 `24h 新增 Star ÷（当前累计 Star - 24h 新增 Star）` 估算，用于识别小体量项目的爆发强度。

## 最值得深入研究的 3 个项目

### 1. [mattpocock/skills](https://github.com/mattpocock/skills)

它已连续热门并升至第一，且近期内容直接涉及规格实现和代码审查流程。建议重点拆解 Skill 的边界、依赖、触发条件、验收步骤和跨工具安装方式，再映射到团队代码审查中的“规则加载—证据收集—问题分类—修复验证”链路。

### 2. [mahlernim/google-timeline-visualizer](https://github.com/mahlernim/google-timeline-visualizer)

相对日增接近 89%，是典型的小体量爆发项目。它把高度敏感、结构复杂的个人数据转成直观成果，同时主打本地处理，值得研究其导入容错、隐私边界、地图渲染和视频输出闭环；这类“本地数据加工 + 可分享产物”的产品模式可迁移到更多个人 AI 工具。

### 3. [PostHog/posthog](https://github.com/PostHog/posthog)

它把产品分析、实验、错误和 AI 可观测性放在同一平台，对生产 Agent 尤其重要。建议研究如何让代码审查结果与真实用户事件、异常、Feature Flag 和回滚信号关联，使审查从静态代码判断走向“上线前规则 + 上线后证据”的闭环；同时先核查许可证、数据合规和部署成本。
