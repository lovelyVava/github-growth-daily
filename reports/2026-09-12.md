## 统计口径与限制

1. **24 小时新增 Star**：采用 GitHub Trending 日榜的 `stars today`；这是滚动窗口，不等于自然日或相邻快照差。页面顺序不严格按该值排序，本报告按数值重新排序。
2. **7 天新增 Star**：采用周榜的 `stars this week`。只有公开周榜直接展示的数值才写入；未进入周榜的项目标为“缺失”，不从累计 Star 反推。
3. **当前 Star/Fork**：采用 2026-09-12 08:00–08:05 的 GitHub API 快照。Trending 与 API 抓取时间略有不同，因此累计数可能存在小幅时差。
4. **Fork 变化**：仅对连续进入前十的项目比较 9 月 11 日与 9 月 12 日相邻快照；新上榜或重新上榜项目不估算 24 小时 Fork 变化。
5. **工程活跃度**：统计 2026-09-05 00:00 UTC 起约 7 天的默认分支提交，单仓最多读取 100 条；触及上限写作“≥100”。
6. **贡献者活跃度**：按提交记录中的 GitHub 账号或作者邮箱去重估算，可能拆分同一人的多个身份或包含机器人；截断仓库写作下限，不等同累计 Contributors。
7. **讨论热度**：统计同一窗口新建 Issue，排除 PR。若接口首 100 条记录仍落在窗口内，则写作下限；Issue 数量不等于有效人工讨论。
8. **许可证识别**：GitHub API 对 `gods-eye-view`、`llm_wiki` 和 `armorpaint` 返回 `NOASSERTION`，本报告进一步读取许可证正文，分别识别为“代码 MIT、第三方数据/资产另行授权”、GPL-3.0 和 zlib/libpng。
9. **爆发原因**：根据 README、近期活动与榜单表现作分析推断，不代表维护者官方结论。

## 项目分析

### 1. bilawalsidhu/gods-eye-view

- **主要用途**：在浏览器 3D 地球上统一展示航班、船舶、卫星、地震、火情、交通、公共摄像头和无线电等开放信号，并支持语音控制与场景分析。
- **技术栈**：JavaScript、Vite、Cesium/WebGL、GLSL、公开地理与遥测 API、可选 OpenAI 实时语音 Agent；代码采用 MIT License，数据与 3D 资产另行授权。
- **近期增长**：日榜约 **+3,680 Star**、周榜约 **+8,916 Star**；相对日增约 **15.7%**。当前 27,057 Star、5,542 Fork；较上期 Fork 约 **+506**，排名上升 1 位。
- **贡献与讨论**：近 7 天约 53 次提交、约 9 个作者身份、新 Issue **≥39**；工程活动和贡献广度较昨日显著增强。
- **爆发原因**：逼真的“情报驾驶舱”视觉表现叠加真实公开数据、病毒式演示视频与无需密钥的快速启动，形成持续传播。
- **亮点**：模块化图层、真实/模拟数据标注、目标跟踪、驾驶舱、视域、轨迹、分享链接与语音白板；可本地运行。
- **潜在风险**：TeleGeography 数据为 CC BY-NC-SA，Google/OpenSky 等受商业和配额条款限制；公开摄像头及位置数据存在隐私、误读与双重用途风险；浏览器端 Key 必须限制来源。
- **适合人群**：GIS/OSINT 教学、实时可视化、灾害与交通演示，以及需要 3D 地理交互原型的开发者。
- **值得关注程度**：**★★★★☆**。增长质量提升明显，但商业部署前必须逐项审计数据、资产、密钥和伦理边界。

### 2. ayghri/i-have-adhd

- **主要用途**：为编码 Agent 提供行动优先、限制旁支、短列表和明确下一步的输出规则，降低长回答带来的工作记忆负担。
- **技术栈**：Python、Markdown Skill、Hooks，以及 Claude Code、Codex、Cursor、OpenCode、Gemini、Kimi、Qwen 等多宿主插件配置；MIT License。
- **近期增长**：日榜约 **+3,463 Star**、周榜约 **+13,164 Star**；相对日增约 **9.1%**。当前 41,744 Star、2,362 Fork；较上期 Fork 约 **+163**，排名下降 1 位。
- **贡献与讨论**：近 7 天约 21 次提交、约 6 个作者身份、17 个新 Issue；多语言、可逆安装和输出长度成为主要讨论方向。
- **爆发原因**：编码 Agent 输出膨胀是普遍痛点；规则简单、多宿主、复制即用，传播门槛很低。
- **亮点**：强调行动优先、列表上限、可见进展、具体时间估算和每轮状态重述。
- **潜在风险**：过度压缩可能省略证据和安全边界；医疗化命名易被误解为诊断；复杂任务不宜全局套用。
- **适合人群**：容易被长回答淹没的学习者、开发者，以及需要短步骤和明确下一动作的 Agent 团队。
- **值得关注程度**：**★★★★☆**。适合作为可开关的简洁模式，而非所有任务的固定输出层。

### 5. nashsu/llm_wiki

- **主要用途**：把 PDF、Office、网页、图片、音视频等资料增量编译成可追溯、互相链接的个人 Wiki，并提供搜索、知识图谱、深度研究和 Agent 工具。
- **技术栈**：Tauri v2/Rust、React 19、TypeScript、Vite、Milkdown、sigma.js/graphology、可选 LanceDB、MinerU、本地 HTTP API 与 MCP；GPL-3.0。
- **近期增长**：日榜约 **+647 Star**；周榜值缺失；相对日增约 **3.6%**。当前 18,721 Star、2,134 Fork；首次进入近期前十。
- **贡献与讨论**：近 7 天无默认分支可检索提交和活跃作者、12 个新 Issue；最近推送为 8 月 25 日，当前增长主要来自传播回潮。
- **爆发原因**：相较每次从头检索的传统 RAG，“原始资料→持久 Wiki→Schema”更接近可积累的个人知识系统；Obsidian 兼容、来源字段和知识图谱具有明确吸引力。
- **亮点**：SHA256 增量缓存、`sources[]` 来源追踪、多格式解析、四信号图谱关联、Louvain 聚类、可选本地模型和本地 MinerU、MCP/Skill 接入。
- **潜在风险**：两步 LLM 摄入仍可能把错误固化进 Wiki；API Key 通过 Tauri Store 保存，敏感文档是否出站取决于 Provider；Shell 工具、网页抓取与本地 API 扩大权限面；GPL 对分发有传染性要求。
- **适合人群**：Obsidian 用户、RAG/知识图谱研究者、个人研究资料管理和需要文档证据链的 Agent 团队。
- **值得关注程度**：**★★★★★**。架构与现有 Obsidian、RAG 和幻觉治理目标高度契合，但需先补“生成内容与原文逐条核验”层。
