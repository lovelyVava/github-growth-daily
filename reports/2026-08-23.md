## 数据口径与限制

1. **24 小时新增 Star**：采用 GitHub Trending 日榜观察时刻显示的 `stars today`，属于滚动窗口近似值。GitHub 页面展示顺序不完全等于该数值大小，本报告按日增 Star 重新排序。
2. **7 天新增 Star**：采用周榜显示的 `stars this week`。未进入周榜可见范围时标记“缺失”，不使用累计 Star 倒推。
3. **Fork**：累计 Fork 来自本期仓库 API 快照；连续上榜项目以本期减上一期快照得到约 24h Fork 增量。该差值受采样时点影响，统一标为“快照估算”；新上榜项目的 Fork 增量缺失。
4. **贡献活跃度**：近 7 天提交数来自最近 100 条提交按 `created_at >= 2026-08-16` 过滤；达到 100 时记为“≥100（截断）”。新建 Issue/PR 来自同日起的 GitHub Search 计数，包含已关闭项、机器人和自动同步，不能等同于独立贡献者人数。
5. **讨论热度**：列出近 7 天新建 Issue/PR 和 Discussions 是否启用；未取得统一口径的 Discussion 新增/评论数。累计开放项为 Issue 与 PR 合计快照。
6. **相对日增**：按 `24h 新增 Star ÷（当前累计 Star - 24h 新增 Star）` 估算，用于识别小体量项目爆发强度。
7. **许可证**：采用仓库 API 的 SPDX 识别结果；`missing` 或 `NOASSERTION` 均表示必须进一步查阅仓库文件和组件条款，不能理解为可任意商用。

## 最值得深入研究的 3 个项目

### 1. [openai/codex](https://github.com/openai/codex)

它是今天最值得结合 Open Code Review 深挖的项目。建议重点研究沙箱与批准机制、工具调用协议、补丁生成、会话恢复、仓库指令加载以及非交互执行路径，再映射到“IDE 日常辅助—提交前扫描—GitLab 上线前全量审查”的三段式闭环。尤其要区分本地开发权限、服务器审查权限和模型服务凭据。

### 2. [mattpocock/skills](https://github.com/mattpocock/skills)

它连续第一，说明 Skills 已从个人提示词变成可传播工程资产。建议把现有 Open Code Review 的 `background.md`、`rules.json` 和后续规则包按“触发条件—所需证据—检查步骤—结果格式—修复验证”拆成小技能，并建立版本、来源、权限和冲突检查，而不是不断扩充一个超长规则文件。

### 3. [PostHog/posthog](https://github.com/PostHog/posthog)

它适合补上代码审查体系常缺失的“上线后证据”。建议研究如何把审查问题、发布版本、Feature Flag、异常、用户行为和回滚信号关联起来，让规则能够根据真实生产结果校正优先级。采用前需先评估自建复杂度、数据脱敏、保留周期和许可证边界。
