## 三、项目逐项分析

### 1. cloudflare/computer

- **主要用途**：为 Agent 提供持久虚拟文件系统和可插拔执行环境，可在容器、Worker 隔离 Shell 或 JavaScript isolate 中运行任务。
- **技术栈**：TypeScript、Cloudflare Workers、Durable Objects、SQLite、FUSE、容器、capnweb RPC、Dynamic Workers；MIT。
- **近期增长**：约 **+2,690 Star/24h**，当前 4,709 Star、236 Fork，相对日增 **57.12%**；较昨日 Fork +114，日增 Star 提高约 237.9%。仓库约 593 次提交、18 个 Issue、4 个 PR并启用 Discussions；精确 7 日新增缺失。
- **爆发原因**：“Give your agent a computer”定位直观，持久文件系统与真实 Linux 执行环境解决 Agent 跨轮任务、制品和工作区恢复问题。
- **亮点**：SQLite 是权威状态；同一 runtime 可切换容器、隔离 Shell 和 JavaScript，并提供 FUSE 同步与示例 Agent。
- **潜在风险**：官方明确标注 Preview、API 不稳定且不适合生产；真实网络、二进制和持久文件会放大权限、数据外泄、费用与供应链风险。
- **适合人群**：Agent 沙箱、Cloudflare 生态、远程执行与持久工作区原型团队。
- **值得关注程度**：**★★★★★**。今日绝对与相对增速均第一，但应先做隔离和成本验证。

### 2. mattpocock/skills

- **主要用途**：一套面向真实工程的可组合 Agent Skills，重点解决需求误解、设计漂移、架构熵增、交接和异步决策。
- **技术栈**：Markdown Skills、AGENTS/CLAUDE 配置、npm `skills` 安装器、Claude 插件；MIT。
- **近期增长**：约 **+2,002 Star/24h**，当前 206,854 Star、17,866 Fork，相对日增 0.97%。仓库约 420 次提交、286 个 Issue、2 个 PR并启用 Discussions；精确 7 日和 24 小时 Fork 缺失。
- **爆发原因**：`grill-me`、`to-spec`、`handoff` 等技能把“先澄清再执行”做成可复用流程，并明确支持 Codex 等多种 Agent。
- **亮点**：Skill 小而可改，强调保留人的控制权；覆盖需求访谈、规格、架构改进、任务分流、教学和交接。
- **潜在风险**：高累计 Star 使相对增速有限；大量 Skills 可能互相触发或增加上下文，且安装脚本、hooks 与外部指令需要供应链审查。
- **适合人群**：使用 Codex/Claude/Cursor 的资深工程师、研发效能与流程设计团队。
- **值得关注程度**：**★★★★☆**。传播极强，适合拆解工作流，不宜未经裁剪整包引入企业环境。

### 3. firecrawl/pdf-inspector

- **主要用途**：识别文本型、扫描型、图像型或混合 PDF，在无需 OCR 时提取位置感知文本和 Markdown，为文档管线逐页路由。
- **技术栈**：Rust、`lopdf`、PyO3、Node.js/N-API、WebAssembly、CLI；MIT。
- **近期增长**：约 **+1,194 Star/24h**，当前 12,346 Star、828 Fork，相对日增 9.67%；较昨日 Fork +76。约 428 次提交、38 个 Issue、47 个 PR并启用 Discussions；近四份日报累计下限 +7,070 Star，但精确滚动 7 日值缺失。
- **爆发原因**：企业 RAG 希望避免对所有 PDF 盲目 OCR；分类、表格、CID 字体、多栏和按页回退更贴近生产管线。
- **亮点**：单次加载完成分类与提取，支持 Python、Node 和浏览器；可输出置信度、坐标、字体和损坏编码信号。
- **潜在风险**：项目不执行 OCR，手写、极端排版与损坏字体仍可能误判；项目方性能数据需用真实附件独立复测。
- **适合人群**：RAG、文档 ETL、爬虫、法务/财务附件与代码审查规范文档处理团队。
- **值得关注程度**：**★★★★★**。连续高增，边界清晰且容易做小范围落地验证。

### 4. TencentCloud/TencentDB-Agent-Memory

- **主要用途**：团队级 Agent 记忆中心，把会话、文档和代码沉淀为 Chat Memory、Skill、Wiki、CodeGraph 四类可治理资产。
- **技术栈**：TypeScript、多服务架构、Docker、LLM API、BM25/向量检索/RRF、Wiki 与代码图谱；MIT。
- **近期增长**：约 **+1,053 Star/24h**，当前 16,249 Star、1,462 Fork，相对日增 6.48%；周榜约 **+5,445 Star**，较昨日 Fork +99。默认分支约 8 次提交、83 个 Issue、443 个 PR并启用 Discussions。
- **爆发原因**：企业多 Agent 开始需要带 Owner、版本、ACL、状态和绑定关系的团队记忆，而不只是个人聊天记录。
- **亮点**：L0→L3 分层记忆、固定绑定与权限语义、Wiki/CodeGraph、跨 Agent 迁移和团队面板。
- **潜在风险**：集中存储会话、代码和文档会放大隐私、越权、提示注入污染和删除治理风险；默认分支短历史与大量 PR 需要额外审计。
- **适合人群**：Agent 平台、研发效能、知识管理、代码审查和跨会话协作团队。
- **值得关注程度**：**★★★★★**。连续六期上榜且日周双窗口强，是最稳定的企业 Agent 基础设施信号。

### 9. tirth8205/code-review-graph

- **值得关注程度**：**★★★★★**。与企业代码审查最直接相关，优先做真实仓库 A/B 基准。

## 五、当天技术趋势

1. **Agent Skills 从提示集合升级为工程操作系统**  
   mattpocock/skills、agent-skills 与 superpowers 同日入榜，分别强调澄清与架构、完整 SDLC、强制 TDD 与审查。竞争焦点正从“有没有 Skill”转向触发可靠性、组合冲突、eval 和企业门禁。

2. **上下文压缩开始依赖结构化代码图谱**  
   code-review-graph 不再让模型反复扫描全仓库，而是先计算调用、继承、测试覆盖和变更爆炸半径。这条路线与纯向量 RAG 互补，更适合 PR 风险分析。

3. **长任务需要“执行环境 + 状态内核 + 团队记忆”三层栈**  
   Cloudflare Computer 提供文件系统和 runtime，LoopX 管目标、gate、证据与 handoff，TencentDB-Agent-Memory 管跨会话知识资产；三者可以构成可恢复、可审计的 Agent 工作流。

4. **增长从单点工具转向可治理基础设施**  
   今日六个持续项目多数不是单次生成工具，而是运行环境、记忆、流程、状态、文档输入或 Agent Harness。企业采用价值提高，同时权限和供应链面也扩大。

5. **文档输入与知识资产继续高热**  
   pdf-inspector 负责低成本判断和提取，TencentDB-Agent-Memory 负责长期沉淀；二者可组成“附件分类→解析/OCR 路由→Wiki/Skill→审查证据”的输入链。

6. **非代码资源仍可获得大规模传播**  
   ChinaTextbook 说明 Trending 不等于技术成熟度榜；资料仓库应单独评估版权、许可证、来源与可执行文件安全，不能只看 Star。

## 六、最值得深入研究的 3 个项目

### 1. tirth8205/code-review-graph

**理由**：与企业代码审查最直接匹配。可把现有 diff 审查扩展为调用者、依赖、执行路径和测试缺口审查，同时保持本地优先。建议优先在一个中大型真实仓库做 A/B：比较全量上下文与图谱上下文的 Token、召回缺陷、误报、构图时间和增量更新成本，独立验证项目方“中位约 65 倍”结论。

### 2. huangruiteng/loopx

**理由**：objective、gate、todo、evidence、quota、lease 与 handoff 可直接映射到长循环代码审查。重点借鉴有类型的状态转移、人工决策门、证据新鲜度和可验证交接；不要直接照搬自动唤醒，而应接入现有任务队列、权限和预算控制。

### 3. TencentCloud/TencentDB-Agent-Memory

**理由**：连续六期入榜且进入周榜，持续性最强。可将审查规则、架构决策、历史缺陷、代码调用图分别映射为 Skill、Wiki、Chat Memory、CodeGraph，并复用 Owner/版本/ACL；落地前必须完成提示注入隔离、删除治理、最小权限与敏感代码边界设计。

> 次优先：Cloudflare Computer 适合验证 Agent 沙箱和持久工作区，但官方仍处于 Preview；pdf-inspector 适合文档输入层；两套新 Skills 应先做差异分析和固定版本审计，避免与已有流程冲突。

## 七、数据可靠性与限制

- **较可靠**：抓取时累计 Star/Fork、Trending 日/周新增 Star、当前开放 Issue/PR、仓库页面提交总数与许可证展示。
- **估算**：相对日增按当前累计 Star 计算；相邻日报 Fork 差是快照差，不是官方滚动 24 小时指标；“多日报下限”不代表完整 7 日新增。
- **缺失**：未进入周榜可见前列项目的精确 7 日新增 Star；统一口径的 24 小时新增贡献者、Issue 评论和 Discussions 活跃增量。
- **活跃度代理**：提交总数、开放 Issue/PR、Discussions 和相邻快照变化；开放数量多也可能表示积压，数量下降可能来自合并、关闭或整理。
- **抓取误差**：Trending 与仓库详情页缓存时刻不同，Star/Fork 可能有少量差异；报告统一使用日榜快照排序。
- **排序方法**：以日增 Star 为主，再结合周榜、相对增速、Fork 快照和开发活跃度解释；不按累计 Star 排名。
- **许可证提醒**：ChinaTextbook 仓库页面未显示许可证，报告不把“公开可访问”视为获得再分发授权。
