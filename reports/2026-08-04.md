## 三、项目逐项分析

### 1. zhaoxuya520/reverse-skill

- **主要用途**：为 Codex、Claude Code、Cursor 等 Agent 提供逆向工程、授权渗透测试和安全研究的 Skill 路由、工具自举与证据工作流。
- **技术栈**：PowerShell、Shell、Python、Node.js、Skill/MCP；主仓库 MIT，部分子目录或外部工具为 GPL/AGPL 等许可证。
- **近期增长**：约 **+2,442 Star/24h**，当前 15,522 Star、2,198 Fork，相对日增 15.73%；周榜约 **+4,415 Star**。较昨日 Fork +230；仓库约 111 次提交、6 个 Issue、9 个 PR，提交数较昨日增加约 12。
- **爆发原因**：安全研究流程被封装为可安装、自动路由的 Agent Skills，同时覆盖 APK、固件、CTF、API 与供应链，形成很强的演示和传播效应。
- **亮点**：授权范围门禁、证据链、案例初始化和工具索引比单纯提示词更接近可重复的安全作业系统。
- **潜在风险**：明显双用途；自动安装或运行安全工具会扩大网络、主机权限和供应链风险。必须限定授权目标、隔离运行并审计命令。
- **适合人群**：授权安全测试、逆向工程、CTF 与安全平台团队。
- **值得关注程度**：**★★★★★**。日榜第一、周榜第四且相对增速很高，但采用前应先做安全治理。

### 3. firecrawl/pdf-inspector

- **主要用途**：快速判断 PDF 是文本型、扫描型、图像型或混合型，并在无需 OCR 时提取位置感知文本、表格与 Markdown，用于智能路由到本地解析或昂贵 OCR。
- **技术栈**：Rust、`lopdf`、Python 绑定、Node.js/N-API、WebAssembly、CLI；MIT。
- **近期增长**：约 **+1,769 Star/24h**，当前 7,879 Star、528 Fork，相对日增约 **22.45%**，为前十最高；约 414 次提交、25 个 Issue、33 个 PR，未启用 Discussions。精确 7 日增长和 24 小时 Fork 缺失。
- **爆发原因**：RAG、Agent 文档处理和批量爬取都面临“是否值得调用 OCR”的成本决策；纯 Rust、本地运行、浏览器 WASM 与多语言绑定让该组件容易嵌入现有管线。
- **亮点**：一次解析同时完成分类和提取；支持多栏、表格、字体编码、位置数据与逐页 OCR 路由，接口覆盖 Rust、Python、Node 和浏览器。
- **潜在风险**：不包含 OCR；复杂字体、手写、极端版式和损坏 PDF 仍可能误判。README 中约 20ms 分类、150ms 提取及“约 54% PDF 无需 OCR”是项目方口径，需要独立基准验证。
- **适合人群**：RAG/知识库、文档 ETL、爬虫、法务/财务文档处理和浏览器端 PDF 工具团队。
- **值得关注程度**：**★★★★★**。增长最快且解决明确的成本瓶颈，适合立即做真实语料基准测试。

### 5. lyogavin/AirLLM

- **主要用途**：通过逐层或逐专家流式加载，在低显存设备上运行超大语言模型；项目宣称 70B 模型可在 4GB GPU 上推理。
- **技术栈**：Python、PyTorch、Transformers、safetensors、bitsandbytes、MLX、CUDA；Apache-2.0。
- **近期增长**：约 **+1,081 Star/24h**，当前 26,901 Star、2,956 Fork，相对日增 4.02%；周榜约 **+1,588 Star**，较昨日 Fork +81。约 308 次提交、94 个 Issue、28 个 PR并启用 Discussions。
- **爆发原因**：超大 MoE 模型支持与“低于 4GB 显存”形成强传播点，本地模型用户希望以容量换取可运行性。
- **亮点**：显存需求取决于单层或激活专家而非模型总量；支持分层存储、预取和可选压缩。
- **潜在风险**：低显存不等于高速度，磁盘、I/O、内存、首轮拆分和每 Token 延迟仍可能成为瓶颈；AMD ROCm 与 Radeon 9070 XT 兼容性仍缺少可靠公开确认。
- **适合人群**：本地 LLM 实验、低显存推理研究、希望验证超大模型而不追求高吞吐的开发者。
- **值得关注程度**：**★★★★★**。连续日榜且进入周榜，但必须用真实硬件验证性能宣传。

## 六、最值得深入研究的 3 个项目

### 1. pdf-inspector

**理由**：它解决的是文档 AI 管线中一个具体、可量化的成本问题：何时本地解析、何时调用 OCR。Rust 核心加 Python、Node、WASM 多端绑定，适合直接接入原型。建议用真实合同、论文、扫描件和多栏财报测分类准确率、Markdown 保真度、P95 延迟与 OCR 节省比例。

### 2. TencentDB-Agent-Memory

**理由**：连续三期上榜，日榜信号由 342、604 增至 1,091，Fork 快照本日再增 107。团队记忆很可能成为多 Agent 协作的基础设施层，四类资产和多服务架构值得研究；同时必须测试租户隔离、删除、权限继承与提示注入污染。

### 3. AirLLM

**理由**：连续日榜并进入周榜，低显存运行超大模型仍有明确需求。研究重点应从宣传中的“能运行”转为可重复的硬件矩阵：安装兼容、磁盘占用、模型预处理时间、首 Token 延迟、吞吐、功耗和 CUDA/MLX/ROCm 差异。

> 次优先：`reverse-skill` 适合研究 Agent 安全作业系统，但要先建立隔离和授权边界；`DeepSeek-Reasonix` 适合研究长期运行的 Coding Agent Harness；`voicebox` 对游戏语音和 AI NPC 很有启发，但声音权利和模型许可证需优先治理。

## 七、数据可靠性与限制

- **较可靠**：抓取时累计 Star/Fork、Trending 日/周新增 Star、当前开放 Issue/PR、仓库页面提交总数与许可证。
- **估算**：相对日增按当前累计 Star 计算；相邻日报 Fork 差是快照差，不是官方滚动 24 小时指标。
- **缺失**：未进入周榜项目的精确 7 日新增 Star；统一口径的 24 小时新增贡献者、Issue 评论和 Discussions 活跃增量。
- **活跃度代理**：提交总数、开放 Issue/PR、Discussions 和相邻快照变化；开放数量多也可能意味着积压，不能单独解释为健康社区。
- **排序方法**：以日增 Star 为主，再结合周榜、相对增速、Fork 快照和开发活跃度解释；不按累计 Star 排名。
